# 自动驾驶领域 STL 数据生成任务说明

## 1. 任务目标

基于当前目录顶层已有的场景、信号、领域知识、STL 模板和输出格式资料，逐个评估 STL 模板在各自动驾驶场景中的适用性。对于适合的“模板-场景”组合，生成语义自然、数值合理、可验证的 STL/NL 双语数据；对于不适合的组合，不得强行生成，并记录明确的失败原因。

本任务应支持长时间、分批次执行。考虑 Codex 单次上下文/token 额度以及每 5 小时额度恢复，必须采用逐条验证、逐条落盘和断点续作机制。

## 2. 可读取的输入范围

只允许读取当前目录顶层的 `.txt`、`.md`、`.kb` 文件。不要读取任何子目录及其下文件。

当前资料及用途如下：

- `file_explain.txt`：各输入文件用途说明。
- `6_template.txt`：STL 模板，共 877 个非空且互不重复的模板；每行一个模板。
- `auto_driving_scene_signals_refine.txt`：场景、场景描述、可用信号和推荐谓词。
- `auto_driving_scene_signals_explain_refine.txt`：各场景信号的简明解释、类型、单位和部分定义。
- `auto_driving_scene_signals.kb`：详细领域知识、信号约束、定义和使用注意事项。
- `STL.md`：STL 语法及算子语义参考。
- `data_format.txt`：单条数据的 JSON 字段、双语文本及算子追踪要求。

场景共 10 个：AEB、ACC、Lane Keeping、Parking、Traction Control、Traffic Light、Speed Limit、Intersection、Pedestrian and Cyclist、Lane Change。

## 3. 总体覆盖方式

原则上逐一评估全部 877 个模板在 10 个场景中的适用性，即评估 877 × 10 个“模板-场景”组合。

- 每个组合都必须被处理并留下可恢复的完成状态。
- 对一个适合的组合，生成一条最自然、最合理的数据即可。
- 不要求每个组合都成功生成数据。
- 不允许为了覆盖模板或增加数据量而强行填充公式。
- 一个组合被判定不适合时，应写入失败说明并继续下一个组合。

## 4. 适合生成数据的判断标准

只有同时满足以下条件，候选数据才可进入最终数据集：

1. 公式中的所有信号都属于当前场景，不跨场景借用信号，不虚构资料中不存在的信号。
2. 谓词、布尔结构、时间区间和 STL 算子均符合模板及 `STL.md` 的语义。
3. 谓词组合符合当前场景的真实工程逻辑，不存在明显矛盾、错误因果或无意义拼接。
4. 从 STL 公式反向翻译出的自然语言容易理解，并且像正常的驾驶系统需求或工程规约。
5. 直译完整保留公式语义；意译在表达自然的同时，不遗漏、不增强、不削弱公式语义。
6. 中英文直译彼此一致，中英文意译彼此一致，直译与意译之间也保持语义一致。
7. 所有阈值、单位、时间参数和信号定义均合理且可解释。

如果公式虽然语法可成立，但翻译后别扭、不自然、难以理解，或者不像人们正常表达的工程需求，应判定为不适合，不得强行翻译。

## 5. 谓词和数值选择

谓词必须根据具体模板和具体场景酌情选择，不能机械套用 `recommended_predicates`。推荐谓词是优先候选，不是唯一来源；任何实际使用的谓词都必须能由当前场景资料中的信号定义和领域知识支持。

每个具体数值必须单独验证合理性：

- 检查信号单位、类型、方向定义和取值范围。
- 检查阈值是否符合该驾驶场景的常识和工程意义。
- 检查同一公式内多个阈值是否相互协调。
- 检查时间窗口是否与相应车辆动作、感知响应或控制响应的时间尺度匹配。
- 区间参数应满足必要的顺序关系，例如 `0 <= t1 < t2 < t3`。
- 优先使用推荐谓词或领域资料中已有的阈值。
- 若使用资料中未直接给出的数值，必须有合理的场景依据，且应在内部验证和必要的失败说明中体现判断依据。
- 不得仅因为某个数值能够填入模板就认为它合理。

## 6. rise/fall 边沿算子的特殊要求

包含 `rise` 或 `fall` 的模板必须谨慎处理。核心要求是：准确保留状态切换或阈值跨越的算子语义，同时使用自然的工程语言，不能使用僵硬的逻辑定义式翻译。

### 6.1 基本原则

- 不得把 `rise(P)` 简化为“P 成立”。
- 不得把 `fall(P)`仅翻译成“P 下降”，因为数值下降不一定会使谓词由成立变为不成立。
- 不要机械翻译成“P 从假变真”或“P 从真变假”。这些是逻辑语义说明，不是正常工程语言。
- 应结合谓词方向和场景，用“开始……”“进入……状态”“达到/越过……阈值”“风险出现”“介入启动”“条件解除”“恢复到……范围”“退出……状态”“介入结束”等自然表达体现边沿语义。
- 具体措辞不能使用固定替换表，应由信号、比较符、阈值和上下文共同决定。

例如：

- `rise(ttc < 2.5)` 可自然表达为“碰撞时间缩短至 2.5 秒以内时”。
- `fall(ttc < 2.5)` 可自然表达为“碰撞时间恢复至不低于 2.5 秒时”。
- `rise(aeb_active == 1)` 可表达为“AEB 开始介入时”。
- `fall(aeb_active == 1)` 可表达为“AEB 结束介入时”。

这些只是表达方式示例，不应机械复制到不匹配的场景。

### 6.2 复合谓词边沿

对于 `rise(P and Q)`、`fall(P and Q)` 等复合谓词，边沿作用于整个复合条件：

- 必须体现整个复合条件刚刚出现或解除的语义。
- 不得错误解释为 P 和 Q 分别出现独立边沿。
- 不要僵硬地写成“(P and Q) 从假变真”或“从真变假”。
- 可根据场景自然表达为“当……且……的条件首次同时满足时”“当车辆进入……且……的状态时”“当……情况下又出现……时”“当……情况解除时”等。

例如，`rise(traffic_light_red == 1 and stop_line_distance < 30)` 可结合场景表达为“当车辆在距停车线不足 30 米时遇到红灯”，前提是上下文确实能够体现该复合触发条件刚刚出现。

### 6.3 边沿适用性和验证

- 只有状态切换、模式启停、事件发生、风险出现/解除或阈值穿越具有自然工程含义时，才使用边沿模板生成数据。
- 若无法同时做到“边沿语义准确”和“表达自然”，应放弃该模板-场景组合。
- 独立验证器必须额外检查边沿方向、作用域和触发时刻。
- `rise(speed > 60)` 与 `rise(speed < 60)` 的自然表达方向不同，不能因为都使用 `rise` 就翻译成相同动作。
- 验证复合谓词边沿是否被错误拆分。
- 验证边沿是否被弱化为普通状态描述。

## 7. 单条数据生成流程

对每个“模板-场景”组合按以下流程处理：

1. 读取并解析模板中的谓词槽位、时间参数、布尔结构、时序算子和边沿算子。
2. 从当前场景选择语义相关且实际可用的信号与谓词。
3. 验证所有具体阈值、单位和时间参数的合理性。
4. 生成完整 STL 公式。
5. 按 `data_format.txt` 生成中英文公式直译和中英文工程意译。
6. 做本地/确定性检查：信号归属、模板保持、语法、括号、单位、参数顺序、字段完整性、JSON 可解析性等。
7. 使用独立 LLM 对该条候选数据做语义一致性验证。
8. 若验证失败，根据反馈修改候选，再使用一个新的独立验证调用重新检查。
9. 建议最多修订和验证 3 次。多次迭代后仍不自然、不一致或数值难以合理化，则放弃该组合并记录失败原因。
10. 验证通过后，立即将该条数据写入独立文件，并立即追加相应追踪信息；完成落盘后再处理下一条。

## 8. 独立 LLM 验证要求

每条候选数据必须使用独立、无共享对话历史的 LLM 调用验证，不能让前一条数据或前一次验证结论影响当前判断。

给验证 LLM 的信息应足够但精简，只提供：

- 当前 STL 模板。
- 填充后的完整 STL 公式。
- 当前公式实际用到的必要信号解释、单位和阈值依据。
- 中英文直译。
- 中英文意译。
- 当前公式涉及的必要 STL 算子语义。

不要提供与当前数据无关的大段场景资料或其他候选数据。

验证器至少需要判断：

1. STL 与中文直译、英文直译是否语义等价。
2. 直译与中英文意译是否等价。
3. 时序算子的区间、方向、作用域和嵌套关系是否被正确表达。
4. `rise/fall` 的边沿语义、方向、作用域和触发时刻是否正确且自然。
5. 是否存在语义遗漏、额外承诺、条件增强或条件削弱。
6. 谓词和数值在当前驾驶场景中是否合理。
7. 最终表达是否自然、清楚并像真实工程规约。

验证失败时必须返回具体反馈，用于下一轮修订。重新验证必须是新的独立调用。

## 9. 单条 JSON 数据格式

每条成功数据必须严格遵循 `data_format.txt` 给出的字段：

```text
{
    id,
    stl_template,
    domain,
    scene,
    trace_info,
    stl,
    signals_info,
    time_info,
    nl_Literal_translation_en,
    nl_Literal_translation_zh,
    nl_Paraphrase_en,
    nl_Paraphrase_zh
}
```

要求：

- 输出必须是严格合法 JSON，键名和字符串均使用双引号。
- `id` 从 `00000` 开始连续编号。
- 只有验证通过并成功落盘的数据才占用 ID。
- `stl_template` 保留使用的模板原文。
- `trace_info` 记录模板中时间参数和谓词槽位到实际填充值的对应关系。
- `signals_info` 只描述公式实际使用的信号，并包含必要单位信息。
- `time_info` 说明公式实际使用的时间值及单位。
- 四个 NL 字段必须同时存在并通过一致性验证。

## 10. 成功数据逐条落盘

每条成功数据单独保存到：

```text
./output/dataset/step1/00000.json
./output/dataset/step1/00001.json
./output/dataset/step1/00002.json
...
```

必须“处理完一条，立即追加一条”，不得等整个批次完成后统一写入。这里的“追加”指新增下一个独立 JSON 文件。

为避免中断产生半文件：

1. 先写入同目录临时文件。
2. 对临时文件执行 JSON 解析和字段完整性检查。
3. 检查通过后原子重命名为最终编号文件。
4. 最终文件生成后再递增下一个 ID。

不得覆盖已经存在且验证完成的数据文件。

## 11. 失败说明

所有不适合生成或多次验证仍失败的组合，立即追加到：

```text
./output/fail_translation_explain.txt
```

每条失败记录至少包含：

- 稳定组合标识，例如模板序号加场景名。
- 模板序号和模板原文。
- 当前场景。
- 考虑过的信号和谓词。
- 相关数值合理性判断。
- 不适合生成的具体原因。
- 若进入过 LLM 验证，记录主要反馈、迭代次数和最终放弃原因。

失败原因应具体，例如边沿无自然工程意义、过去时态关系难以由当前信号自然表达、谓词组合因果不成立、阈值无法合理确定、直译虽可完成但意译极不自然等。不要只写“无法翻译”。

## 12. 算子与触发词追踪

每条成功数据落盘后，立即追加两类追踪：

```text
./output/operator_trigger_literal_translation.txt
./output/operator_trigger_paraphrase.txt
```

每条追踪必须包含数据 ID，并同时包含中文和英文部分。

只追踪：

- 时序算子：`always`、`eventually`、`until`、`historically`、`once`、`since`。
- 边沿算子：`rise`、`fall`。

不需要单独追踪 `and`、`or`、`not`、`->` 等布尔算子。

追踪要求：

- 直译追踪文件记录每个算子及其在中英文直译中的对应表达。
- 意译追踪文件记录公式片段及其在中英文工程意译中的对应表达。
- 对嵌套算子分别追踪其作用域和对应语言片段。
- `rise/fall` 必须追踪完整作用域及自然表达，证明边沿语义没有丢失。
- 复合谓词边沿不能被追踪成多个独立边沿。

## 13. 断点续作和 token 额度管理

任务规模较大，必须假设执行会因上下文/token 额度耗尽而暂停，并在额度恢复或新窗口中继续。

使用进度文件：

```text
./output/dataset/step1/progress.json
```

进度至少记录：

- 当前或下一个模板序号。
- 当前或下一个场景序号/名称。
- 下一个成功数据 ID。
- 已完成组合数。
- 成功数和失败数。
- 最后完成的稳定组合标识。
- 必要的版本或输入文件校验信息，防止输入变化后错误续跑。

执行规则：

- 每完成一个模板-场景组合，就更新进度文件。
- 成功数据、追踪、失败记录和进度之间应采用可恢复的写入顺序。
- 恢复时先扫描已有 JSON 文件、失败记录和进度文件，交叉校验后再确定续跑位置。
- 已完成组合不得重复处理。
- 失败记录应使用稳定组合标识，避免恢复后重复追加。
- 成功 ID 仅在完整 JSON 已验证并正式落盘后递增。
- 接近额度限制时，只能停在一个组合完整处理完毕之后，不能留下待验证或半写入状态。
- 每个小批次结束时检查 JSON 合法性、ID 连续性、重复组合、追踪完整性和进度一致性。

## 14. 最终质量检查

全部组合处理完成后，应执行最终检查并形成汇总：

- 877 个模板是否全部被评估。
- 10 个场景是否均按计划参与评估。
- 已处理组合总数是否与预期一致。
- 成功和失败组合是否都有记录，是否存在遗漏或重复。
- 成功 JSON 是否全部可解析、字段完整且 ID 连续。
- 每条成功数据是否都有直译追踪和意译追踪。
- 是否存在跨场景信号、未知信号、单位错误或不合理阈值。
- 各模板、各场景的成功/失败数量分布。
- 包含 `rise/fall` 的成功数据是否都通过专项边沿语义检查。

## 15. 执行中的最高优先级原则

1. 不强行生成 STL，不强行翻译。
2. 语义一致性优先于数据数量。
3. 数值和单位必须合理，不能只保证语法成立。
4. `rise/fall` 的算子语义不能丢，但表达也不能僵硬。
5. 每条数据必须独立验证，通过后立即落盘。
6. 所有工作必须支持中断后可靠续作。
